From story to design · feature + interface
1 — FEATURE DESIGN ROW (features.md)

  List simulation instances | Story 1 | Retrieve all simulations belonging to a student so they can
  choose which to inspect | Student records, simulation IDs, status, elapsed time


2 — FUNCTION INTERFACE

  simulationList(studentId)                               DESIGN TRADE-OFFS

  {                                                       • simulationId, required by the AC
      simulations: [                                      • status + timeElapsed - useful summary
        {
          simulationId: 1,                                • NOT full course/exam data - this is a list/summary
          simulationStatus: 'ACTIVE',                     • Want detail? call simulationStatus later
          timeElapsed: 0,
        }
      ]
  }
Step 3 — the stub (src/simulation.js)

 // Return a summary list of all simulation
 // instances belonging to a student.
                                              A stub proves the SHAPE
 function simulationList(studentId) {
                                              of a function, not the logic.
   return {
      simulations: [
         {
           simulationId: 1,
           simulationStatus: 'ACTIVE',        • No real behaviour
           timeElapsed: 0,                    • Just a sample object matching the
         }                                      interface
      ],
   };
 }

Teamwork advice & wrap-up

 FIVE HABITS                                  A USEFUL REVIEW COMMENT
 • Work small - one task per issue & MR       ✗ “looks good”
 • Review meaningfully (not “looks good”)
 • Never modify prescribed interfaces         ✓ “The interface row says simulationList
                                              returns simulationStatus, but the stub returns
 • Keep master clean - it's what you submit   status. Can we make the names match?”
 • Resolve conflicts as a team
